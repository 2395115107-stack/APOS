# Agent Interface

## 目标

`AGENT_INTERFACE.md` 规定 APOS 中所有 agent 与工作环境（文件、命令、工具、报告）的统一接口。

它来源于三个工程判断：

- SWE-agent 论文：agent 与计算机的接口设计会显著影响软件工程表现
- Anthropic context engineering：上下文的目标是最小的高信号 token 集，而不是塞满一切
- OpenAI harness engineering：关键约束应尽量机械化，agent 看不到的东西等于不存在

所有 workflow 和 agent 文件如果与本文件冲突，以本文件为准；如果与产品目标冲突，以产品目标为准并记录到 `05-memory/DECISIONS.md`。

---

## 核心原则

1. **文件是唯一交接介质**：任务信息靠文件传递，不靠对话记忆
2. **返回只传状态与路径**：详细内容落文件，主上下文只保留必要信号
3. **路径即契约**：所有输入、输出、回写必须写明确路径，不写"相关文件"
4. **上下文最小化**：每个 agent 只读当前任务所需文件，按需展开
5. **输出结构固定**：统一使用 `Owner / Next / Inputs / Outputs / Skills / Writeback`

---

## 读文件约定

### 默认读取顺序

agent 接到任务后，按需读取，不要求全读：

1. 当前任务在 `02-product/TASKS.md` 中的条目
2. 任务条目中列出的 `Inputs` 文件
3. 与任务直接相关的 memory：`DECISIONS.md`、`LESSONS.md` 中相关条目
4. 对应 workflow 和 agent 定义

不默认读取的：

- 其它任务的条目
- 与当前任务无关的 memory 条目
- 全部 references

### 读取行为

- 先读目录和索引，再按需展开具体文件
- 长文件先读结构（标题），再定位到相关小节
- 如果输入文件不存在，立即写 `BLOCKED` 并说明缺什么，不要凭空假设内容

---

## 写文件约定

### 路径规则

- 一律写从仓库根目录出发的相对路径，例如 `02-product/TASKS.md`
- 禁止只写文件名（`TASKS.md`）或口头指代（"上面那个文件"）
- 新建目录时同步创建最小 README 或说明，不留空目录

### 编辑规则

- 修改前先读原文件，不覆盖未知内容
- 保持文档现有结构：标题层级、分隔线、字段格式
- 追加条目放在对应章节末尾，遵循已有条目格式
- 一次编辑只做一类变更，便于 review 定位

### 报告落盘位置

review / test / 评估报告默认写入：

```text
10-reports/{RUN-ID}/
```

例如 `10-reports/RUN-20260704-001/review.md`。

- `RUN-ID` 来自 `05-memory/RUNS.md` 的本次运行编号
- planner 在任务条目中可以指定其它报告路径；未指定时使用默认位置
- 报告文件头部必须写明：任务、时间、结论（PASS / FAIL）、问题数量

---

## 修改报告约定

agent 完成修改后，向主编排者返回的内容不超过一个输出块：

```text
状态：完成 / 阻塞 / 需要重试
Owner: {当前角色}
Next: {下一角色}
Outputs: {产物路径列表}
Skills: {使用过的 skill；未使用则写 none}
Notes: {一句话必要说明，如偏离原方案、遗留风险}
```

禁止在返回中粘贴：

- 大段代码或大段文档内容
- 完整测试输出（只留结论和失败项）
- 过程叙述（写到报告文件里）

---

## 命令运行约定

- 运行测试、构建、检查命令前，先说明要运行什么、预期输出是什么
- 命令失败时保留关键错误信息到报告文件，不在对话里反复重试同一命令
- 不运行 `05-memory/DECISIONS.md` 或 `04-development/PERMISSIONS.md` 中标记为高风险的操作，除非有人工确认记录

---

## 测试与评审报告格式

所有 tester 和 reviewer 的报告使用统一骨架：

```text
# {Review / Test} Report: {任务标题}

RUN: {RUN-ID}
Date: {日期}
结论: PASS / FAIL
阻塞问题: {数量}

## 问题列表

- [严重度] 位置：{文件路径或行为描述}
  影响：{一句话}
  建议：{一句话}

## 已验证项

- {通过检查的简短列表}
```

严重度取值：

- `BLOCKER`：必须修复才能进入下一步
- `MAJOR`：必须修复才能完成任务
- `MINOR`：应该修复，可进入下一轮
- `NIT`：可选修复，不阻塞

---

## 失败处理约定

- 工具或命令失败：记录错误 + 已尝试内容 + 建议，写 `BLOCKED` 或回报告告
- 输入不完整：明确列出缺失文件和缺失字段，不猜测补全
- 修正循环：按 `07-workflows/review.md` 和 `new-feature.md` 的轮次上限执行，重测只验证失败项

---

## 上下文预算

每个 agent 的返回和处理都应遵循"最小高信号集"：

- 交接块 ≤ 10 行
- 报告只保留结论、问题列表、已验证项
- 引用已有内容用路径，不复制原文
- 如果一个任务的上下文必然很大，planner 应拆任务，而不是让单个 agent 读全部

---

## 反模式

- 把大段实现说明直接塞回主对话
- 写"已修复相关问题"而不列出具体路径
- 凭记忆修改没读过的文件
- 测试输出只说"有几个失败"而不落报告
- 在一个 agent 的上下文里堆满所有无关文档
